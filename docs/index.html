C++20 · single producer, single consumer

A command buffer for two threads

One thread records commands and another executes them, in order. A command is a type and a plain-data payload in one ring of bytes, and the executing thread decodes it with a switch. Recording a command allocates nothing and takes no lock, and a thread with nothing to do sleeps instead of spinning. This guide builds the whole thing one decision at a time, following Kaspar Daugaard's three articles on SPSC ring buffers. Every snippet is taken from the working code in this guide's repository.

Goal

What we are building

A render thread is the classic case. The game thread decides what to draw; the render thread talks to the graphics API. The game thread should not stall on the graphics driver, and the render thread should not see game state halfway through an update. So the game thread writes a list of self-contained commands and the render thread replays them. This is where we will end up. On the game thread:

examples/RenderThreadExample.cppsimplified
RenderCommandBuffer commands(256 * 1024);  // capacity in bytes
Renderer renderer;                          // from here on, only touched by the render thread
std::thread renderThread(&RenderCommandBuffer::ExecuteUntilStopped, &commands, std::ref(renderer));

for (int frame = 0; frame < frameCount; ++frame)
{
    commands.SetClearColor(Color{pulse, 0.2f, 0.3f});   // writes kCmd_SetClearColor, then the color
    for (const Object& object : objects)
        commands.Draw(object.mesh, object.transform);   // writes kCmd_Draw, then mesh and transform
    commands.Present(frame);
    commands.Submit();                                  // the render thread may start on this frame
}

commands.SubmitStop();
renderThread.join();

And on the render thread, which waits until a command is ready, reads its type and payload, and executes it:

examples/RenderThreadExample.cppRenderCommandBuffer, abridged
void ExecuteUntilStopped(Renderer& renderer)
{
    cb::CommandType type;
    while (ReadCommand(type))                           // waits for the next command; false after SubmitStop()
    {
        switch (type)
        {
            case kCmd_SetClearColor:
            {
                renderer.SetClearColor(ReadPayload<Color>());
                break;
            }

            case kCmd_Draw:
            {
                const DrawPayload& payload = ReadPayload<DrawPayload>();
                renderer.Draw(payload.mesh, payload.transform);
                break;
            }

            case kCmd_Present:
            {
                renderer.Present(ReadPayload<int>());
                break;
            }
        }
        FinishCommand();
    }
}

The requirements behind that interface:

  • Commands differ in size. Setting a clear color takes a few bytes; uploading a mesh carries kilobytes of vertex data.
  • Recording must be cheap. A frame can have thousands of commands, so there can be no heap allocation and no lock per command.
  • One writer, one reader. This restriction is what keeps the lock-free design simple. If several threads record, each gets its own buffer.
  • Idle threads sleep. A render thread with nothing to render must not burn a core, and waking it must cost the game thread nothing in the common case.
  • The producer can wait for the consumer. For example, to keep at most two frames in flight.

The code has three layers. SpscRingBuffer moves bytes from one thread to the other. CommandBuffer writes and reads command types and payloads in those bytes, and handles batches, waiting and stopping. Your own class, RenderCommandBuffer here, defines the commands: one producer function and one case each. Steps 1 to 11 build the ring buffer, step 12 the commands.

Starting point

The obvious version

Most people start with the textbook thread-safe queue. It has three parts: a container that holds the commands, a mutex that makes the container safe to use from two threads, and a condition variable that lets the consumer sleep while there is nothing to do. This is the version the measurements compare against:

bench/Benchmark.cppthe baseline
// Every command is a fixed-size struct, pushed and popped under a mutex.
struct QueuedCommand
{
    cb::CommandType type;
    std::uint64_t value;
};

struct MutexQueue
{
    std::mutex mutex;
    std::condition_variable notEmpty;
    std::deque<QueuedCommand> queue;
    std::uint64_t sum = 0;

    void Push(const QueuedCommand& command)   // game thread
    {
        {
            std::lock_guard lock(mutex);
            queue.push_back(command);
        }
        notEmpty.notify_one();
    }

    QueuedCommand Pop()                        // render thread
    {
        std::unique_lock lock(mutex);
        while (queue.empty())
            notEmpty.wait(lock);
        QueuedCommand command = queue.front();
        queue.pop_front();
        return command;
    }

    void ExecuteUntilStopped()                 // render thread
    {
        for (;;)
        {
            QueuedCommand command = Pop();
            switch (command.type)
            {
                case kCmd_Add:
                {
                    sum += command.value;
                    break;
                }
                case cb::kCmd_Stop:
                {
                    return;
                }
            }
        }
    }
};

The benchmark starts the render thread on ExecuteUntilStopped(), pushes 20 million commands from the game thread, and ends with kCmd_Stop:

bench/Benchmark.cppRunMutexQueue()
MutexQueue queue;
std::thread consumer(&MutexQueue::ExecuteUntilStopped, &queue);   // the render thread
for (std::uint64_t i = 0; i < kCommands; ++i)
    queue.Push(QueuedCommand{kCmd_Add, i});
queue.Push(QueuedCommand{cb::kCmd_Stop, 0});
consumer.join();

The rest of this section walks through each piece. If it is all familiar, skip to why it is slow.

The command type

Every element of the queue has the same type, so every command gets the same fixed-size slot: a type and one 8-byte payload. That works for the benchmark's kCmd_Add. A Draw command with a 16-byte payload would not fit, unless value became a union as large as the biggest command, and then every command pays for the biggest one. A CreateMesh with its vertex array would need a pointer to separately allocated memory. That limit is why step 1 switches to a ring of raw bytes, where each command takes exactly the space it needs.

What each member is for

std::dequethe commands

The commands waiting to run, oldest first. A deque ("double-ended queue") adds at the back and removes from the front in constant time. A std::vector would be wrong here, because removing its first element shifts every other element down by one. A std::list allocates memory for every single element. A std::queue would be the same thing, because by default it is a thin wrapper around a std::deque.

A deque has no fixed capacity. It allocates more memory blocks as it grows, so the producer never waits for space, and the queue keeps growing if the consumer falls behind. In MSVC's implementation a block holds 16 bytes, which for these 16-byte commands means one block per command whenever the queue grows. The ring buffer is the opposite: fixed capacity, and the producer waits when it is full.

std::mutexprotects the deque

std::deque is not thread-safe. A push_back on one thread at the same moment as a pop_front on the other can corrupt its internal pointers. That is a data race, and undefined behavior. So every access to queue happens while the mutex is locked, and only one thread can hold it at a time.

std::lock_guard and std::unique_lock lock the mutex in their constructor and unlock it in their destructor, so the mutex is released on every way out of the scope.

std::condition_variablewakes the consumer

Lets the consumer sleep until there is work. Without it, the render thread would have to lock, check, unlock and repeat in a loop, and burn a whole core while waiting. A condition variable is usually named after the condition it announces; here, "the queue is not empty".

sumbenchmark only

The consumer's "work": kCmd_Add adds its value, so the benchmark can check the result at the end. It is not part of the queue.

How the condition variable is used

A condition variable always works together with a mutex and a condition that you check yourself, here !queue.empty(). It has a waiting side and a notifying side:

Pop()render thread, the waiting side
std::unique_lock lock(mutex);          // 1. lock the mutex
while (queue.empty())                  // 2. check the condition while holding it
    notEmpty.wait(lock);               // 3. unlock and sleep; lock again when woken
QueuedCommand command = queue.front();
queue.pop_front();
return command;                        // 4. the unique_lock's destructor unlocks
Push()game thread, the notifying side
{
    std::lock_guard lock(mutex);       // 1. lock the mutex
    queue.push_back(command);          // 2. change the state while holding it
}                                      // 3. the lock_guard's destructor unlocks
notEmpty.notify_one();                 // 4. wake one waiting thread, if any

wait(lock) does three things: it unlocks the mutex, puts the thread to sleep, and, when the thread is woken, locks the mutex again before returning. Unlocking and going to sleep happen as one step, and that is the key detail. If they were two separate steps, the producer could push a command and notify in the gap between them. The notification would reach nobody, and the consumer would sleep with a command waiting. That is the same lost wake-up that step 9 solves by hand for the ring buffer, with a flag, a re-check and sequentially consistent operations.

  • Why std::unique_lock in Pop(). wait() has to unlock and relock the mutex. A std::lock_guard can never be unlocked before its destructor runs; a std::unique_lock can. Push() never needs that, so the simpler lock_guard is enough there.
  • Why while and not if. A thread may wake up without anyone notifying it, a "spurious wakeup" that the standard allows. So the condition is checked again after every wake-up, and the thread continues only when the queue really has something in it.
  • Why the extra braces in Push(). They end the lock_guard's scope, so the mutex is unlocked before notify_one(). If the producer notified while still holding the mutex, the consumer would wake up and immediately block on that same locked mutex. Both orders are correct; notifying after unlocking avoids the wasted round trip.

Why it is slow

The queue is correct, and for a few hundred commands per frame it is fine. But its costs come with every single command:

  • Both threads lock and unlock the same mutex. Each lock and unlock is an atomic operation on one shared cache line, which keeps moving between the two cores. The deque's internal pointers move between the cores too.
  • The producer calls notify_one(). That is a call into the operating system's condition-variable code every time: cheap when nobody is waiting, and a real kernel wake-up when the consumer is asleep.
  • The deque allocates memory whenever it grows, and every command is as large as the largest one.

On the test machine it moves 20 million commands at 47 ns each. The finished command buffer runs the same benchmark at 3.1 to 3.5 ns per command when the producer submits in batches. On its fast path each thread writes only to its own cache line, the two threads synchronize only at Submit() or when one of them has to wait, and nothing is allocated. The measurements section has the details.

Step 1 of 13

Bytes, not elements

Most lock-free queues are an array of one element type: slot i holds item i. Commands have different sizes, and a fixed slot size either wastes memory or needs a pointer to somewhere else, which brings allocation back. So this ring holds raw bytes, and each side asks for exactly as many as it needs.

The second decision is to separate reserving space from making it visible. The producer can reserve and fill many pieces and then hand all of them over at once. The consumer can read many pieces and give their space back at once:

include/cb/SpscRingBuffer.hthe core API
// Producer
void* PrepareWrite(std::size_t size, std::size_t alignment); // reserve bytes to fill in
void  FinishWrite();                                         // publish everything written so far

// Consumer
void* PrepareRead(std::size_t size, std::size_t alignment);  // the next bytes, same size as written
void  FinishRead();                                          // release everything read so far

Typed helpers sit on top. Write and WriteArray copy plain data; Emplace constructs an object in place; Read returns a reference into the ring, so the consumer uses the data where it lies:

include/cb/SpscRingBuffer.h
template <class T>
void Write(const T& value)
{
    static_assert(std::is_trivially_copyable_v<T>, "Write() copies bytes; use Emplace() for other types");
    std::memcpy(PrepareWrite(sizeof(T), alignof(T)), &value, sizeof(T));
}

template <class T, class... Args>
T& Emplace(Args&&... args)
{
    return *::new (PrepareWrite(sizeof(T), alignof(T))) T(std::forward<Args>(args)...);
}

template <class T>
T& Read()
{
    return *std::launder(static_cast<T*>(PrepareRead(sizeof(T), alignof(T))));
}

Used directly, the ring buffer already works as a command buffer: write a command type, then its data, and switch on the type when reading. This is how Daugaard's article presents it, and it is the shape the command layer in step 12 builds on:

raw ring bufferillustration
// Producer
ring.Write(kCmd_CreateMesh);
ring.Write(meshId);
ring.Write(vertexCount);
ring.WriteArray(vertices, vertexCount);
ring.FinishWrite();                       // now the consumer can see all four pieces

// Consumer
switch (ring.Read<CommandType>())
{
    case kCmd_CreateMesh:
    {
        int meshId = ring.Read<int>();
        std::uint32_t count = ring.Read<std::uint32_t>();
        const float* vertices = ring.ReadArray<float>(count);   // used in place, no copy
        renderer.CreateMesh(meshId, vertices, count);
        break;
    }
}
ring.FinishRead();                        // the producer may reuse those bytes

Reading in place is fast, and it comes with one rule that everything else depends on:

Rule 1

The consumer reads the same sizes, with the same alignments, in the same order as the producer wrote them. Writing two 4-byte values and reading one 8-byte value is a bug even though the bytes are identical. Step 6 shows why.

Step 2 of 13

Stream positions instead of indices

Each side needs to know how far it has got. The usual approach stores an index into the array and wraps it with a modulo or a mask. Then "read index equals write index" means empty, and to tell a full buffer from an empty one you either waste a slot or keep a separate count.

Daugaard's version counts differently. Think of every byte ever written as one endless stream. A stream position is an offset into that stream: it only grows and is never wrapped. Each thread stores its position in two parts:

include/cb/SpscRingBuffer.hLocalState, abridged
std::size_t base; // stream position of buffer[0] in the current lap: 0, capacity, 2 * capacity, ...
std::size_t pos;  // offset inside the buffer, 0 <= pos <= capacity
                  // stream position = base + pos

The thread works with the small offset pos on its fast path, and shares the full stream position with the other thread. Comparing stream positions answers every question directly:

QuestionTest on stream positions
Is the buffer empty?published == released
Is it full?written − released == capacity
May the producer write up to stream position e?e ≤ released + capacity
May the consumer read up to e?e ≤ published

No slot is wasted and nothing is masked. The original code asks for a power-of-two capacity; with this scheme nothing depends on that, so this version accepts any size.

Positions are size_t and keep growing, so they will eventually wrap past zero. On a 64-bit build that takes centuries; on a 32-bit build it is 4 GB, a few seconds of heavy traffic. It is harmless either way, because the code never compares two positions with <. It subtracts them and looks at the sign:

include/cb/SpscRingBuffer.h
// `to - from` as a signed number. Stream positions only move forward and the two sides
// stay within two laps of each other, so this is right even after size_t wraps to 0.
static std::ptrdiff_t Distance(std::size_t from, std::size_t to)
{
    return static_cast<std::ptrdiff_t>(to - from);
}

The true difference between the two threads' positions is always small, and unsigned subtraction followed by a signed cast recovers it even when one value has wrapped and the other has not.

TestedRingBuffer_TwoThreads_PositionOverflow starts the stream 50,000 bytes below SIZE_MAX and streams half a million records across the wrap. With Distance() replaced by a plain comparison, the test hangs.

Step 3 of 13

Local state, shared state, and cache lines

Caches move memory in 64-byte lines. To write to a line, a core must own it exclusively, so a write on one core invalidates every other core's copy, and the next access on those cores waits for the line to come back. This happens even when two threads write different variables that merely share a line, which is called false sharing. A small benchmark in this repository shows the effect: two threads, each incrementing only its own counter.

Each LocalState holds everything its thread needs on the fast path. The buffer pointer and capacity are stored twice, once per side, so the producer never reads a line the consumer writes. The two SharedState lines hold the one number the other thread needs: the published position.

include/cb/SpscRingBuffer.h
// State only one thread ever touches. It stays in that core's cache.
struct alignas(kCacheLineSize) LocalState
{
    char*       buffer = nullptr;
    std::size_t pos  = 0; // offset of the next byte to write or read, in [0, size]
    std::size_t end  = 0; // [pos, end) is known to be usable without looking at the other thread
    std::size_t base = 0; // stream position of buffer[0] in the current lap (grows by `size` per lap)
    std::size_t size = 0; // capacity; duplicated in both states so neither side reads the other's line
    // Consumer only, for FinishReadLazy() (step 11):
    std::size_t finished  = 0;
    std::size_t published = 0;
    std::size_t lazyLimit = 0;
};

// State one thread writes and the other reads: one cache line per writer.
struct alignas(kCacheLineSize) SharedState
{
    std::atomic<std::size_t> pos{0};      // stream position published by the owning thread
    std::atomic<bool> peerWaiting{false}; // the other thread sleeps until `pos` changes (step 9)
};

LocalState  m_Writer;       // producer only
LocalState  m_Reader;       // consumer only
SharedState m_WriterShared; // written by the producer, read by the consumer
SharedState m_ReaderShared; // written by the consumer, read by the producer

The field that makes this layout pay off is end, a cached limit. [pos, end) is a range the thread already knows it may use: free space for the producer, published data for the consumer. As long as an allocation stays below end, the thread touches only its own cache line. Only when it runs past end does it load the other thread's position and recompute end. The starting values describe an empty buffer:

include/cb/SpscRingBuffer.hconstructor
m_Writer.end = capacity; // empty buffer: the producer may fill all of it...
m_Reader.end = 0;        // ...and the consumer has nothing to read yet

Step 4 of 13

The fast path

With the cached limit in place, reserving space is a handful of instructions:

include/cb/SpscRingBuffer.h
CB_FORCE_INLINE void* PrepareWrite(std::size_t size, std::size_t alignment)
{
    std::size_t pos = AlignUp(m_Writer.pos, alignment);
    std::size_t end = pos + size;
    if (end > m_Writer.end) [[unlikely]]
        WriteSlowPath(pos, end);
    m_Writer.pos = end;
    return m_Writer.buffer + pos;
}

CB_FORCE_INLINE void* PrepareRead(std::size_t size, std::size_t alignment)
{
    std::size_t pos = AlignUp(m_Reader.pos, alignment);
    std::size_t end = pos + size;
    if (end > m_Reader.end) [[unlikely]]
        ReadSlowPath(pos, end);
    m_Reader.pos = end;
    return m_Reader.buffer + pos;
}

Align, add, compare, store. The comparison with the cached end is the only branch. Everything else (wrapping, refreshing end, waiting) lives in WriteSlowPath() and ReadSlowPath(), which are marked CB_NOINLINE. The fast path is marked CB_FORCE_INLINE so the compiler inlines it into every Write() and every recorded command; because it is tiny, that does not bloat the code.

Inlining matters more than it looks. In Daugaard's comparison, boost::lockfree::spsc_queue took 42 s for a billion ints at -Os and 12 s at -Ofast, against 1.2 s for his buffer, and he attributes much of the gap to poor inlining.

The two slow paths are both new and mirror images of each other. Both start the same way: if the block does not fit before the end of the buffer, wrap. Step 6 covers that part; step 8 covers the rest.

Step 5 of 13

Alignment

Commands hold doubles, pointers and SIMD types, so each allocation rounds the position up to its alignment first:

include/cb/SpscRingBuffer.h
static std::size_t AlignUp(std::size_t pos, std::size_t alignment)
{
    assert(alignment != 0 && (alignment & (alignment - 1)) == 0 && alignment <= kCacheLineSize);
    return (pos + alignment - 1) & ~(alignment - 1);
}

The offset is aligned relative to the start of the storage, so the storage itself must be aligned at least as strictly. The constructor allocates it with ::operator new(capacity, std::align_val_t{64}), which supports any alignment up to 64 bytes. A type declared alignas(128) trips the assert.

When the alignment is a compile-time constant and the compiler can see the previous write, which is usual once PrepareWrite() is inlined, the rounding often folds away. The article lists two alternatives for code where it does not: ignore alignment entirely if every type is fine with the buffer's natural alignment, or round every size up to a common minimum so pos is always aligned already.

Rule 1 covers alignment too. If the producer aligns a block to 16 and the consumer asks for 8, the consumer starts reading inside the padding.

TestedRingBuffer_Alignment writes blocks with alignments 1, 32, 2 and 64, checks that they land at offsets 0, 32, 64 and 128, and that the consumer gets back the very same addresses.

Step 6 of 13

Wrapping around with a gap

A block must be contiguous: the consumer gets one pointer and uses the bytes in place, so a block cannot start at the end of the buffer and continue at the beginning. When the next block does not fit before the physical end, the producer leaves the rest of the lap empty and puts the block at offset 0 of the next lap:

include/cb/SpscRingBuffer.hWriteSlowPath(), first part
std::size_t base = m_Writer.base;
if (end > m_Writer.size)
{
    // The block does not fit before the physical end of the buffer. Leave the rest of
    // this lap as a gap and start the block at offset 0 of the next lap. The consumer
    // makes the same decision on its own, because it reads the same sizes.
    end -= pos;
    pos = 0;
    base += m_Writer.size;
}

The producer writes no marker into the gap. The consumer reaches the same conclusion from the same arithmetic: it aligns its position, adds the size, sees that the end passes the capacity, and skips to the next lap. That is the reason for rule 1. If the consumer read two 4-byte values as one 8-byte value near the end of the buffer, the two sides would make different wrap decisions, and every byte after that would be misread.

The alternative is a "magic ring buffer" that maps the same physical memory twice in a row, so a block can run off the end and continue at the start. It needs OS-specific virtual memory calls and page-sized buffers. A gap wastes less than one block per lap, which is a small price for portable code.

Background

Memory ordering

Steps 7 to 11 depend on four memory orders: relaxed, acquire, release and seq_cst. This section explains the problem they solve, what each one guarantees, what it costs, and where this code uses it. If you know all that already, skip to step 7.

Why the order of memory operations is not a given

The producer's code says: write the command bytes, then store the new position. The consumer relies on seeing them in that order. Three things can change the order in which another thread observes them:

  • The compiler may reorder, merge or remove loads and stores, as long as a single thread could not tell the difference. It may also keep a variable in a register: a loop like while (!ready) {} on a plain bool can become a loop that never reads memory again.
  • The CPU executes instructions out of order. A store first goes into the core's store buffer and reaches the cache, where other cores can see it, a little later. Meanwhile the core keeps running, including the loads that come after the store.
  • Weakly ordered CPUs such as ARM may also make two stores, or two loads, to different addresses visible in the opposite order.

One thing is always guaranteed: coherence. For any single memory location, all cores agree on one order of the writes to it. The trouble is always about the order of accesses to different locations, such as the command bytes and the position. Which reorderings the hardware itself performs, for ordinary loads and stores to different addresses:

An access, then a later access to another addressCan appear swapped on x86-64on ARMv8
store, then storenoyes
load, then loadnoyes
load, then storenoyes
store, then load (the store buffer)yesyes

The compiler may perform any of the four on either CPU. C++ therefore handles this in the language. If two threads access the same ordinary variable, at least one of them writes, and nothing orders the accesses, that is a data race, and the whole program has undefined behavior. std::atomic is the way out: an atomic operation is never torn and never races. Its std::memory_order argument says how it orders the other memory accesses around it, ordinary ones included.

Two patterns, two different answers

Two small "litmus tests" capture almost everything this code needs. The first is message passing: one thread writes data and then sets a flag; the other sees the flag and reads the data.

producer
data = 42; // an ordinary int
ready.store(true, std::memory_order_release);
consumer
if (ready.load(std::memory_order_acquire))
    Use(data); // sees 42

Release and acquire are exactly enough here. If the acquire load sees true, the consumer is guaranteed to see 42, on any CPU, whatever the compiler does. With relaxed instead, it might see the old value of data, and since data is an ordinary variable the program would have a data race. Publishing a position in step 7 is this pattern.

The second is store buffering: each thread stores to its own variable, then loads the other thread's.

thread A
x.store(1, order);
r1 = y.load(order);
thread B
y.store(1, order);
r2 = x.load(order);

Can both loads return 0? If each store were visible before the next load ran, no: whichever load runs last must see the other thread's store. But with release and acquire, yes. Both stores can still sit in their store buffers while both loads read the old values from the cache. Only seq_cst rules this out. The sleep handshake in step 9 is this pattern: "store my position, then check whether you are asleep" against "store that I am asleep, then check your position". If both checks read the old value, both threads sleep forever.

The memory orders

Each atomic operation takes one of these. The guarantee is about the operations around it in the same thread, as seen from other threads.

memory_order_relaxedloads, stores, read-modify-writes

Only atomicity: the operation is indivisible, and all threads see the writes to this one variable in the same order. Nothing is promised about other variables.

Here: FinishReadLazy() checks the producer's peerWaiting flag with a relaxed load. It is only a hint. If the value is stale, the release happens a little later anyway, at the next check or before the consumer waits.

memory_order_releasestores, read-modify-writes

No read or write that comes before the store in program order may become visible after it. Everything the thread did before the store is published together with it.

Here: the meaning of every position the producer publishes and the consumer releases (the code uses seq_cst for those stores, which includes release).

memory_order_acquireloads, read-modify-writes

No read or write that comes after the load may happen before it. If an acquire load reads the value a release store wrote, the store synchronizes with the load: everything before the store is visible to everything after the load.

Here: every load of the other thread's position in the slow paths and in WaitForPeer()'s spin.

memory_order_acq_relread-modify-writes

Acquire and release at once, for operations that read and write in one step: exchange, fetch_add, compare_exchange.

Here: not used. The exchanges in the handshake are seq_cst, which includes it.

memory_order_seq_csteverything · the default

Acquire for loads, release for stores, acq_rel for read-modify-writes, and one more guarantee: all seq_cst operations in the program form a single total order that every thread agrees on, and that keeps each thread's program order. In practice, a seq_cst store followed by a seq_cst load of another variable can no longer swap, which is what store buffering needs.

Here: the four operations of the sleep handshake in Publish() and WaitForPeer(), and the exchanges that resolve it.

memory_order_consumeloads

Meant as a cheaper acquire for data reached through the loaded pointer. Compilers implement it as acquire, and its use has been discouraged since C++17. You can ignore it.

Read-modify-write operations have one more property that the handshake depends on, whatever their memory order: they always read the latest value in the variable's order of writes, and write in the same indivisible step. When two threads both call exchange(false) on a flag that is true, exactly one of them gets true back.

Happens-before: why the command bytes need no atomics

Inside one thread, statements are ordered by program order: each is sequenced before the next. Between threads, order comes only from synchronizes-with edges, when an acquire load reads what a release store wrote. Happens-before is any chain of these two kinds of edges. If every access to some ordinary memory on one thread happens before every conflicting access on the other thread, there is no data race. That is why only the two positions in the ring buffer are atomic, and the command bytes are plain memory:

Rules of thumb

  • Start from seq_cst, the default, and weaken one operation at a time, with the reason written in a comment next to it.
  • To publish data, use a release store and an acquire load of the same atomic variable.
  • For "store mine, then check yours" between two threads, use seq_cst on all four operations. A std::atomic_thread_fence(std::memory_order_seq_cst) between the store and the load, on both sides, also works.
  • Use relaxed only for values that nothing else depends on: counters, statistics, hints.
  • volatile is not a synchronization tool in C++. It gives no atomicity and no ordering between threads. MSVC gives it acquire and release meaning on x86 and x64 as an extension (/volatile:ms), which is not portable.
  • x86 hides ordering bugs, because its hardware reorders so little. Code that is right on x86 by luck can fail on ARM, or after the compiler reorders it. Litmus programs and stress tests on real hardware catch some of these bugs. Reasoning about happens-before catches the rest.

Step 7 of 13

Publishing with release and acquire

So far each thread only touches its own state. The threads meet at two points: the producer publishing its position, and the consumer releasing its own. In Daugaard's first version these are a release store and an acquire load:

version 1as in the first article
void FinishWrite()
{
    m_WriterShared.pos.store(m_Writer.base + m_Writer.pos, std::memory_order_release);
}

// in ReadSlowPath():
std::size_t writerPos = m_WriterShared.pos.load(std::memory_order_acquire);

Because the position is a std::atomic<size_t>, neither thread can see half a number. The memory orders do the real work. A release store guarantees that every write the producer made before it, the command bytes included, is visible to a thread whose acquire load reads the stored value. Without that guarantee the compiler or the CPU could make the new position visible before the bytes it covers, and the consumer would read garbage.

The same pair runs the other way. FinishRead() stores the consumer's position with release and the producer loads it with acquire before reusing the space, so the consumer is done reading bytes before the producer overwrites them. It also gives the producer a way to see the consumer's results: whatever a command did on the consumer thread is visible to the producer once it has waited for that command.

TestedCommandBuffer_WaitUntilExecutedSynchronizes has commands push into a plain std::vector on the consumer thread, and the producer reads the vector after each wait. The test itself uses no atomics; the ring buffer's release and acquire provide the ordering.

On x86 a release store and an acquire load compile to ordinary mov instructions, because the hardware already keeps those orders. They still matter there: they stop the compiler from reordering, and on ARM they become the stlr and ldar instructions that the hardware needs. Step 9 strengthens both operations to sequential consistency, for a reason that has nothing to do with the data.

Step 8 of 13

The slow path, and the first deadlock

After the wrap check, each slow path loads the other thread's position, checks whether the block fits, waits if it does not, and recomputes its cached end:

include/cb/SpscRingBuffer.h
CB_NOINLINE void WriteSlowPath(std::size_t& pos, std::size_t& end)
{
    assert(end - pos <= m_Writer.size && "a single allocation must fit in the ring buffer");
    std::size_t base = m_Writer.base;
    if (end > m_Writer.size)
    {
        end -= pos;                     // wrap, see step 6
        pos = 0;
        base += m_Writer.size;
    }

    // The producer may run at most one full buffer ahead of what the consumer released,
    // so the consumer must have released everything up to `required`.
    std::size_t required = base + end - m_Writer.size;
    std::size_t readerPos = m_ReaderShared.pos.load(std::memory_order_acquire);
    if (Distance(required, readerPos) < 0)
    {
        // Never wait while holding unpublished data: the consumer may need exactly that
        // data before it can release the space we are waiting for.
        FinishWrite();
        readerPos = WaitForPeer(m_ReaderShared, m_WriterWakeup, required);
    }
    m_Writer.base = base;
    m_Writer.end = std::min(readerPos + m_Writer.size - base, m_Writer.size);
}

Every wait in the ring buffer has the same form: wait until the other thread's position reaches a required stream position. The producer needs the consumer to have released up to one capacity behind the end of the new block. The new end is then the consumer's released position plus one capacity, expressed as an offset in the producer's current lap, and capped at the physical end. ReadSlowPath() is the mirror image: it needs the producer to have published up to the end of the block, and its new limit is the producer's published position, also capped at the end of the buffer.

include/cb/SpscRingBuffer.hReadSlowPath(), after the wrap check
// The producer must have published everything up to `required`.
std::size_t required = base + end;

m_Reader.end = std::min(writerPos - base, m_Reader.size);

Look at the FinishWrite() before the wait. Without it, this happens: the producer records a large frame without submitting, the buffer fills, and the producer waits for space. The consumer, meanwhile, has run out of published data and waits for the producer. The data it needs is sitting right there in the buffer, unpublished. Neither thread moves again.

Rule 2

Never wait while holding data the other thread needs. Before the producer waits for space, it publishes what it has written. The consumer may then start on a command whose second half is not written yet; it simply waits at that read like at any other.

This is what makes large batches safe: CommandBuffer users call Submit() once per frame, however big the frame is.

The consumer has the mirror-image problem, and it cannot fix it the same way. Read() returns references into the ring, so the ring cannot release bytes behind the consumer's back while it might still be using them. There is a limit instead:

Rule 3

While the consumer waits for the rest of a message, the bytes it holds plus the bytes the producer still has to write must fit in the buffer. In practice: release after each message, and keep a message well under half the capacity, because a wrap can add a gap almost as large as one block. CommandBuffer asserts that each command is at most half the capacity.

Step 9 of 13

Sleeping without losing wake-ups

Version 1 waits by spinning: it reloads the other thread's position in a loop. That is fine when each thread has its own core and waits are short. It is bad when a wait is long, because a render thread with nothing to render burns an entire core. It is worse when the other thread is not running at all, because the spinning thread takes the CPU time that thread needs. Daugaard's third article replaces the spin with a semaphore. The hard part is releasing the semaphore only when someone is actually asleep: releasing it on every FinishWrite() would put an OS call into every publish.

Each SharedState gets a flag, and each thread gets a semaphore to sleep on. A thread that wants to sleep sets peerWaiting in the other thread's shared state. The other thread checks the flag after it publishes, and releases the semaphore only if it is set. Done naively, that loses wake-ups:

#ProducerConsumer
1loads the producer's position: 100. It needs 108.
2stores position 108
3loads peerWaiting: false, so it releases nothing
4stores peerWaiting = true
5sleeps. Its data is there, and nobody will wake it.

If the producer then fills the buffer and waits for the consumer, both threads sleep forever. The fix is to look again after asking:

include/cb/SpscRingBuffer.hWaitForPeer(), the sleeping part
for (;;)
{
    std::size_t pos = peer.pos.load(std::memory_order_acquire);
    if (Distance(required, pos) >= 0)
        return pos;

    // Ask to be woken, then look again: the peer may have published after our load
    // but before it could see the request.
    peer.peerWaiting.store(true, std::memory_order_seq_cst);
    if (peer.pos.load(std::memory_order_seq_cst) != pos)
    {
        // It did publish. Withdraw the request and re-check, unless the peer already
        // took the request, in which case its release() is on the way.
        if (peer.peerWaiting.exchange(false, std::memory_order_seq_cst))
            continue;
    }
    wakeup.acquire();
}
include/cb/SpscRingBuffer.hthe other side
// Store our new position, then wake the other thread if it asked to be woken.
static void Publish(SharedState& mine, std::size_t pos, std::binary_semaphore& peerWakeup)
{
    mine.pos.store(pos, std::memory_order_seq_cst);
    if (mine.peerWaiting.load(std::memory_order_seq_cst)) [[unlikely]]
        WakePeer(mine, peerWakeup);
}

static CB_NOINLINE void WakePeer(SharedState& mine, std::binary_semaphore& peerWakeup)
{
    // Exactly one of us and the peer gets to reset the flag. If the peer reset it first,
    // it withdrew its request and is not going to sleep.
    if (mine.peerWaiting.exchange(false, std::memory_order_seq_cst))
        peerWakeup.release();
}

FinishWrite() and FinishRead() both call Publish(). After setting its flag, the waiting thread reloads the position. If the position changed, the other thread published in between and may or may not have seen the request. Both threads then race to reset the flag with exchange(false), and exactly one wins:

  • The waiting thread wins. The publisher never saw the request and will not release the semaphore. The waiter withdraws and checks the position again.
  • The publisher wins. It has released the semaphore or is about to. The waiter calls acquire(), which returns at once.

Either way every release() is matched by exactly one acquire(), so a std::binary_semaphore is enough. In the common case nobody is asleep, and the publisher pays one extra load of a flag from a cache line it already owns. The exchange only runs when the flag is set.

Why every operation in the handshake is seq_cst

The re-check only helps if the two threads cannot both read stale values: the waiter reading the old position after setting its flag, and the publisher reading the old flag after storing its position. Each thread stores one variable and then loads the other. That is the store-buffering pattern from the memory ordering section, and x86 allows exactly this outcome: a store sits in the core's store buffer while the following load already reads from the cache. Release and acquire do not forbid it; the litmus program there catches it in 4 to 8 percent of trials. Jeff Preshing's Memory Reordering Caught in the Act shows it happening on real hardware.

Making the four operations memory_order_seq_cst forbids it. Sequentially consistent operations form one total order that every thread agrees on, and that order respects each thread's program order. Suppose the publisher's flag load misses the waiter's flag store. Then the load comes before the store in the total order, which gives the chain

the total order
publisher stores pos  →  publisher loads flag  →  waiter stores flag  →  waiter loads pos

so the waiter's load comes after the publisher's store and must see it. At least one side always sees the other.

TestedThis is not theoretical. With these four operations weakened to release and acquire, CommandBuffer_PingPongAlwaysSleeping, RingBuffer_TwoThreads_TinyBuffer and RingBuffer_TwoThreads_NoSpinning hung on every run on the Ryzen 7 9700X.

Daugaard's version publishes with a release store followed by an unconditional exchange, and re-checks with a relaxed load. On x86 that works in practice: the exchange and the sequentially consistent flag store each compile to a locked instruction, which drains the store buffer. That variant passes all 23 tests here. The C++ memory model does not promise it, though, and on ARM a relaxed load may run ahead of an earlier store-release. The version here pays the same price on x86, one locked instruction per publish (the seq_cst store becomes xchg), and is correct on any CPU.

That locked instruction is why publishing after every single 4-byte int costs 5.6 ns here, where Daugaard's version 1 took 1.7 ns. He notes that the semaphore version makes finishing about an order of magnitude more expensive and recommends publishing in larger chunks. Publishing every 256 items brings the cost down to 0.75 ns per int.

TestedRingBuffer_EmptyBufferConsumerSleeps lets the consumer wait 300 ms on an empty buffer and measures its CPU time: 0 µs. RingBuffer_FullBufferProducerSleeps does the same for a producer blocked on a full buffer.

Step 10 of 13

Spin, then sleep

Going to sleep and being woken up costs microseconds. If the other thread is running and will publish within a few hundred nanoseconds, sleeping is a waste. So WaitForPeer() first polls a bounded number of times, then goes through the flag protocol:

include/cb/SpscRingBuffer.hWaitForPeer(), the spinning part
for (std::uint32_t i = 0; i < m_SpinCount; ++i)
{
    CB_CPU_RELAX();
    std::size_t pos = peer.pos.load(std::memory_order_acquire);
    if (Distance(required, pos) >= 0)
        return pos;
}

// CB_CPU_RELAX() is _mm_pause() on x86 and __yield() / "yield" on ARM.

The pause instruction tells the core that this is a spin-wait. It slows the loop down, saves power, and gives the other hyper-thread on the same core more of the shared resources. The spin count is a constructor argument and defaults to 256.

Sleeping at once is still fast on an otherwise idle machine. On a loaded machine a woken thread may have to wait for a free core, so the gap grows. Spinning has a cost of its own, too: the waiting thread keeps reading the other thread's cache line. Keep the spin short.

Step 11 of 13

Releasing lazily

The obvious way for the command layer to give space back is FinishRead() after every command. Measured with the producer submitting every 64 commands, that runs at 42.6 ns per command, no faster than the mutex queue. The cause is step 3's false sharing, one level up. The producer is usually ahead, so it sits in its slow path polling the consumer's released position, and the consumer writes that position after every command. The cache line crosses between the cores once per command.

The fix is to release less often, but the consumer cannot simply release every N commands. A consumer that waits while sitting on finished bytes can deadlock a producer that waits for that space. And a producer waiting for one particular command would also wait for up to N−1 unrelated ones. FinishReadLazy() only records how far the consumer is done, and publishes that position when one of three things happens:

  • A sixteenth of the capacity is pending. A streaming producer gets space back in large chunks, with one cache-line transfer per chunk.
  • The producer is asleep waiting for the consumer. Its peerWaiting flag is set. Checking it is a load from the consumer's own shared line.
  • The consumer is about to wait for data. ReadSlowPath() releases everything finished before it waits, so rule 2 holds on this side too.
include/cb/SpscRingBuffer.h
CB_FORCE_INLINE void FinishReadLazy()
{
    m_Reader.finished = m_Reader.base + m_Reader.pos;
    // The flag is only a hint, so relaxed is enough: if it is stale, the release still
    // happens at a later call or before the consumer waits.
    if (Distance(m_Reader.published, m_Reader.finished) >= static_cast<std::ptrdiff_t>(m_Reader.lazyLimit) ||
        m_ReaderShared.peerWaiting.load(std::memory_order_relaxed)) [[unlikely]]
        FinishRead();
}

// in ReadSlowPath(), before waiting:
if (Distance(required, writerPos) < 0)
{
    // Never wait while holding bytes we are done with (FinishReadLazy()): the producer
    // may be waiting for exactly that space.
    if (m_Reader.published != m_Reader.finished)
    {
        m_Reader.published = m_Reader.finished;
        Publish(m_ReaderShared, m_Reader.published, m_WriterWakeup);
    }
    writerPos = WaitForPeer(m_WriterShared, m_ReaderWakeup, required);
}

With FinishReadLazy() after each command, the same benchmark runs at 3.5 ns per command: twelve times faster than releasing eagerly, and thirteen times faster than the mutex queue. At the ring-buffer level, FinishReadLazy() after every int costs 0.85 ns per int, against 5.6 ns for FinishRead() after every int.

One latency problem remains. Within a batch the consumer releases lazily. Suppose it finishes batch A and starts a slow command from batch B; a producer that now starts waiting for the end of A sits there until the slow command ends. The command layer closes that gap with a marker at the end of each batch, in the next step.

TestedRingBuffer_LazyReleaseBeforeConsumerWaits has the producer wait for every single 4-byte item while the consumer only ever finishes lazily. Remove the release before waiting and the test hangs. Two stress tests run the random-record stream with lazy releases only.

Commands: a type and a payload

A command is a command type, a 4-byte number, followed by a payload of plain data. The game thread calls a function such as commands.SetClearColor(color), which writes kCmd_SetClearColor and then the color. The render thread waits until a command is ready, reads its type, switches on it, reads the payload that belongs to that type, and executes it. Three record shapes cover everything:

// Write a command and its payload. The payload is copied as bytes, so it must be plain
// data: pass handles, indices or pointers for anything that owns memory.
template <class Payload>
void WriteCommand(CommandType type, const Payload& payload) noexcept
{
    static_assert(std::is_trivially_copyable_v<Payload>, "a payload is copied as bytes");
    WriteCommand(type);                       // the type alone
    CheckCommandSize(sizeof(Payload) + alignof(Payload));
    m_Ring.Write<Payload>(payload);
}

// Append an array to the command written last, e.g. vertex data.
template <class T>
void WriteArray(const T* values, std::size_t count) noexcept
{
    CheckCommandSize(sizeof(T) * count + alignof(T));
    m_Ring.WriteArray<T>(values, count);
}

Nothing is allocated: a draw command is 4 bytes of type plus a 16-byte payload, copied straight into the ring. The render thread's side

void ExecuteUntilStopped(Renderer& renderer)
{
    cb::CommandType type;
    while (ReadCommand(type))
    {
        switch (type)
        {
            case kCmd_SetClearColor:
            {
                renderer.SetClearColor(ReadPayload<Color>());
                break;
            }

            case kCmd_CreateMesh:
            {
                const CreateMeshPayload& payload = ReadPayload<CreateMeshPayload>();
                const float* vertices = ReadArray<float>(payload.vertexCount);
                renderer.CreateMesh(payload.mesh, vertices, payload.vertexCount);
                break;
            }

            case kCmd_Draw:
            {
                const DrawPayload& payload = ReadPayload<DrawPayload>();
                renderer.Draw(payload.mesh, payload.transform);
                break;
            }

            case kCmd_Present:
            {
                renderer.Present(ReadPayload<int>());
                break;
            }

            default:
            {
                assert(false && "unknown render command");
                break;
            }
        }
        FinishCommand();
    }
}

ReadPayload() and ReadArray() return references and pointers into the ring itself, so the payload is used where it lies. FinishCommand() gives the command's bytes back lazily (step 11); until then the references stay valid. The render thread starts with a member-function pointer, so no extra code is needed to launch it:

A switch over a dense enum compiles to a jump table, and the payload is read in place, so dispatching a command costs very little. The benchmark moves small commands at 3.1 to 3.5 ns each.

Rule 1 is now in your hands

The consumer must read exactly what the producer wrote for each type: the same payload type, then the same arrays, in the same order. If a case reads a different size or alignment, every command after it is misread. These habits make that hard to get wrong:

  • One payload struct per command. Write it with one WriteCommand() and read it with one ReadPayload() of the same type. Same type means the same size and alignment on both sides. Single values like a Color or an int are their own payload.
  • Read into local variables, in order. Never put two reads in one function call's arguments. C++ does not specify the order in which arguments are evaluated, so renderer.Draw(ReadPayload<int>(), ReadPayload<Transform>()) may read the transform first.
  • Keep the three parts together. Adding a command touches the enum, the producer function and the case. Keep them next to each other, in the same order.
  • Assert in default. An unknown type means the stream is already out of sync.
TestedCommandBuffer_PayloadsRoundTrip interleaves five command types with payloads of up to 44 bytes, including a 32-byte-aligned struct and arrays of 0 to 7 ints, in a 1 KB buffer, and checks every value. With the producer writing payloads without their alignment, the stream goes out of sync and the test hangs.

Batches, tickets and stopping

Submit() ends a batch. It writes the built-in kCmd_EndOfBatch, publishes, and returns a ticket: the stream position just after the marker. ReadCommand() handles the built-in types itself, so your switch never sees them:

include/cb/CommandBuffer.h
Ticket Submit() noexcept
{
    m_Ring.Write<CommandType>(kCmd_EndOfBatch);
    m_Ring.FinishWrite();
    return m_Ring.WritePosition();
}

void WaitUntilExecuted(Ticket ticket) { m_Ring.WaitUntilConsumed(ticket); }

// Wait until a command is ready and return its type. Returns false when the producer
// has called SubmitStop(). The end-of-batch markers written by Submit() are handled here.
bool ReadCommand(CommandType& type) noexcept
{
    for (;;)
    {
        type = m_Ring.Read<CommandType>();
        if (type == kCmd_EndOfBatch)
        {
            // The end of a submitted batch: release right away, the producer may be
            // waiting for it in WaitUntilExecuted().
            m_Ring.FinishRead();
            continue;
        }
        if (type == kCmd_Stop)
        {
            m_Ring.FinishRead();
            return false;
        }
        return true;
    }
}

Inside a batch the consumer releases lazily; at the marker it releases eagerly. So WaitUntilExecuted(ticket) returns as soon as the batch has run, whatever the consumer starts on next, while long batches still pay for almost no synchronization. WaitUntilConsumed() publishes first (rule 2), then waits on the consumer's released position with the same spin-then-sleep logic as everything else. SubmitStop() writes kCmd_Stop, which makes ReadCommand() return false and ends the loop.

TestedCommandBuffer_TicketDoesNotWaitForLaterCommands waits for a batch while the consumer is inside a 400 ms command from the next batch. The wait takes 0 µs. When the marker releases lazily instead, the wait lasts until the slow command finishes and the test fails.
Pitfalls

Plain data only. Payloads are copied as bytes, which a static_assert enforces. To hand over something that owns memory, pass a pointer or handle and decide which thread frees it. Anything a pointer refers to must stay alive until the command has run; frame pacing (next step) bounds how long that is.

One producer. Only the producer thread may call command functions. A case must not record into its own buffer, and must not wait for the producer, since the producer may be waiting for it.

Submit in batches. Every Submit() costs a locked instruction and a cache-line transfer on each side. Submitting after every single command costs 20 ns per command here, six times the batched cost.

A render loop

Put together, a game loop with a render thread and frame pacing looks like this. The full program is examples/RenderThreadExample.cpp.

examples/RenderThreadExample.cpp
RenderCommandBuffer commands(256 * 1024);
Renderer renderer; // from here on, only touched by the render thread
std::thread renderThread(&RenderCommandBuffer::ExecuteUntilStopped, &commands, std::ref(renderer));

// Loading. The game thread picks the mesh handle; the render thread creates the mesh
// when it gets to the command.
const float triangle[] = {0.0f, 0.5f, -0.5f, -0.5f, 0.5f, -0.5f};
const int triangleMesh = 0;
commands.CreateMesh(triangleMesh, triangle, 6);

std::vector<cb::CommandBuffer::Ticket> frameEnd(kFrames);
for (int frame = 0; frame < kFrames; ++frame)
{
    // Frame pacing: wait until the render thread has finished frame N - 2.
    if (frame >= kMaxFramesInFlight)
        commands.WaitUntilExecuted(frameEnd[frame - kMaxFramesInFlight]);

    // Game update, then record this frame's rendering.
    float time = frame / 60.0f;
    commands.SetClearColor(Color{0.5f + 0.5f * std::sin(time), 0.2f, 0.3f});
    for (int i = 0; i < kObjects; ++i)
        commands.Draw(triangleMesh, Transform{std::cos(time + i), std::sin(time + i), time * i});
    commands.Present(frame);
    frameEnd[frame] = commands.Submit();
}

commands.SubmitStop();
renderThread.join(); // the Renderer is ours again

Summary

The contract

Everything the code relies on, in one place:

  1. Exactly one producer thread and exactly one consumer thread.
  2. The consumer reads the same sizes and alignments, in the same order, as the producer wrote. For commands: each case reads exactly the payload and arrays its producer function wrote, one read per statement.
  3. Alignments are powers of two up to 64; a single allocation fits in the capacity.
  4. Data written is invisible to the consumer until FinishWrite() or Submit(), or until the producer has to wait for space.
  5. References from Read() and ReadPayload() are valid until FinishRead() or FinishCommand(), or until a lazy release is published.
  6. The consumer does not wait for new data while holding more than about half the capacity in unfinished reads. Commands are at most half the capacity.
  7. Payloads are plain data. A case does not record into its own buffer and does not wait for the producer.
  8. Publish and submit in batches. Per-item synchronization costs more than all the rest of the work.

Extensions

Going further

  • Several producers. Give each producer thread its own command buffer, and have the consumer drain them in a fixed order, or hand whole recorded buffers over at a sync point.
  • A consumer with other work. A non-blocking TryReadCommand() needs a PrepareRead() variant that returns null instead of waiting.
  • Writing arrays in place. A variant of WriteArray() could return a pointer for the producer to fill, which saves a copy for large uploads.
  • One list of commands. With many commands, the enum, the producer functions and the case labels can be generated from a single X-macro list, so they cannot drift apart.
  • Larger cache lines. Apple M-series cores use 128-byte lines, and some Intel cores prefetch lines in pairs. Raising kCacheLineSize to 128 keeps the separation intact there.
  • Adaptive spinning. The best spin count depends on how long waits usually last. A thread could track how often its spin succeeds and adjust the count.
